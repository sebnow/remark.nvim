# Testing the agent RPC and comment rendering

## Summary

mini.test is the test framework: assertions for the logic and the agent contracts, a child Neovim for the agent-RPC integration test, and screenshots for the rendering.

## Context

The agent write path adds two parts a return value cannot describe. The transport is one. An outside process finds the running session over `nvim --server <addr> --remote-expr` and evaluates a call inside it, so the risk sits in discovery, server startup, argument escaping, and the scheduled redraw, not in the function run on its own. The rendering is the other. Comment threads draw as extmark virtual lines with highlights, text that never enters the buffer and so stays invisible to `nvim_buf_get_lines`.

The rest is pure logic. The store's replay projection and the agent-comment contracts, where an agent appends only a `commented` event and never touches user-owned state (see [attributing comments to their origin](0003-attributing-comments-to-their-origin.md) and [controlling the annotation lifecycle](0004-controlling-the-annotation-lifecycle.md)), are checked by asserting on the result.

mini.test provides assertions, a child-process helper for the wire, and screenshot capture for the rendering, so one framework covers all of it.

Neovim >=0.12 is the target. On it, an external `nvim --server <addr> --remote-expr` reaches a headless Neovim started with `--listen`, runs the call in that process, and returns the result to the caller. mini.test's child is documented to run on `--listen`, so the same client reaches it at a known address.

## Decision

mini.test runs the suite. Its expectations, or a plain `assert` where simpler, check the store projection, the agent contracts, and the log after a wire call.

The RPC integration test starts a mini.test child on a known `--listen` address as the live session, drives it from a separate `nvim --server <addr> --remote-expr` call to the agent entry points, then screenshots the child to confirm the re-render. It drives the real transport rather than an in-process stand-in, since the transport carries the risk. Screenshots check the rendering.

## Options

- **plenary.nvim**, running specs under busted and luassert in a headless Neovim. A larger dependency than mini.test with weaker screenshot support, and it does nothing for the cross-process wire, which still needs spawning by hand. Rejected.
- **busted**, the standard Lua framework. It runs under system Lua, needs setup before it sees the `vim` module, and cannot check the rendering. Rejected.
- **Roll our own, no framework.** `screenstring` and `screenattr` read the same rendered cells mini.test reads, and diffing them against a saved reference is little code, but it reimplements screen capture and a child harness to save one dependency. Rejected.
- **mini.test.** Its assertions, child process, and screenshot capture cover the logic, the wire, and the rendering with one framework. Chosen.

## Consequences

One framework runs everything. The RPC test exercises the real wire and can catch the escaping and discovery faults an in-process call would hide, and the rendering test reads highlights the buffer cannot show.

The suite takes on mini.test as a dependency. The screenshots are reference files, regenerated by hand whenever the rendering changes on purpose and prone to break on Neovim display differences. The RPC test runs slower than a direct call and depends on the child staying reachable at the address the plugin starts it on.
